# Custom hardware inverse design

Run a custom profile on the QPU, then use **Inverse hardware design** in the AI Telemetry Advisor. Select 50% or 80% per-shot survival. The deterministic panel works without an AI key. Apply restores the completed circuit's workload, scale, routing, capacity and interconnect controls into the builder; click Run simulation to verify. It never changes a completed result.

The solver checks captured circuit resources and embedded characterization against a replay of `backend/estimation.py`. Missing historical resources, routing/capacity blockers, inconsistent telemetry, or unrepresentable recipes disable Apply. Rerunning a historical configuration captures current resources. The solver uses expanded native 2Q counts, active circuit width, coherent circuit time including serialized link stalls, and transfers per shot. Shots, readout/reset, repetition pacing and launch overhead affect latency rather than per-shot coherent exposure.

For target S, the balanced recipe multiplies each active point log-loss by `k = log(S) / current_point_log`. Operation errors invert as `-expm1(k*L/count)`; coherence lifetimes divide by k; effective link fidelity becomes `exp(k*link_log/transfers)`. Zero-count subsystems retain their parameters. The recipe scales both defined lifetimes, while preserving null fallback semantics. The sum uses **idle_t1**, never both idle terms. The T2 worst bound is reported separately. These targets are modeled survival, not statistical confidence, measured fidelity or a guarantee of algorithmic success.

Every offered balanced recipe is replayed with full-precision parameters and must match the target natural log within 1e-10. Displayed numbers are rounded; Apply uses original doubles. Finite logs remain useful when probability underflows. A unit operation error produces a certain-failure term, for which proportional scaling is undefined. Extremely large transfer counts can make the required fidelity too close to unity for floating-point representation; these cases report numerical limits rather than claiming a verified recipe.

Single-bottleneck isolation removes the dominant point term to compute the exact survival ceiling with all other losses fixed. If the target exceeds that ceiling, improving that subsystem alone cannot suffice. Otherwise the solver inverts that term alone. A ceiling requiring infinite coherence lifetime is not a finite recipe.

The surface-code bridge scans odd distances 3–35 through the existing reference-calibrated `surface-code.ts` model. It uses recorded physical generator inputs, the custom physical 2Q error, or an explicitly labeled 1e-3 assumed physical baseline for logical profiles. It does not replace an above-threshold physical rate with an optimistic baseline. The minimum error-budget distance and minimum distance passing the **whole-circuit** target are distinct. Only the latter can be applied, after recomputing native resources, d-cycle gate/readout timing and logical-mode survival. The gate proxy's calibrated floor can leave no solution in this range.

Footprints use `2*d²` physical qubits per logical patch for both active circuit width and configured capacity, excluding factories/routing. Equivalent r3 chips use 520 programmable qubits per chip; physical-element counts do not grant programmable capacity. Generated logical profiles use one logical workspace, with physical links and separate T1/T2 decay disabled. Slower logical gates can increase latency even when survival improves. Balanced changes clear stale surface-code generator tags; applying a generated distance records reproducible metadata. Both configurations use existing preset, history and export paths.

The research tests replay applied recipes through the Python backend. For the interactive regression check, start a production preview on port 3107 and run `node scripts/check-inverse-design.mjs` from `frontend/` with Playwright installed. `PLAYWRIGHT_MODULE`, `CHROMIUM_EXECUTABLE` and `PREVIEW_URL` can point to existing installations. It checks 50%/80% application, restoration of dirty controls, the offline advisor, and generated FTQC execution at desktop and mobile widths; simulation responses come from the local Python backend and history/provider traffic is mocked. Tailwind uses the shared PostCSS plugin for both Next bundlers, so webpack previews include the actual dashboard styles.
